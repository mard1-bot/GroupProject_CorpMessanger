# Аудит Безопасности и Ревью перед Деплоем (Production Readiness)

Я провел доскональное ревью конфигураций, Docker-контейнеров, Backend-кода и Frontend-окружения на предмет готовности к переносу на Production VPS. 

Вот детальный отчет о состоянии проекта.

## 1. Безопасность Backend-приложения (Уровень: Высокий 🟢)
- **SQL Инъекции (SQLi):** Весь код в `internal/storage/` использует параметризованные запросы (`$1, $2`) через `database/sql`. Уязвимостей SQL-инъекций нет.
- **Хеширование паролей:** Пароли пользователей безопасно хешируются с использованием алгоритма `bcrypt` (код в `postgres_user.go`).
- **Защита JWT:** Секретный ключ JWT загружается из Docker Secrets. Время жизни сессии задается через конфигурацию (по умолчанию 24 часа), что ограничивает окно возможных атак при краже токена.
- **CORS Политика:** Настроена строгая проверка. `Access-Control-Allow-Origin: *` **не используется**. Заголовки CORS отправляются только в том случае, если источник запроса совпадает со списком `CORS_ORIGINS` из конфигурации.
- **Rate Limiting:** На бэкенде внедрена защита от брутфорса и спама (Rate Limiting Middleware), которая дополнительно усилена Nginx.
- **Drop Privileges (Снижение прав):** В Production Dockerfile (`backend/Dockerfile.prod` или основном `Dockerfile`) процесс приложения запускается от имени непривилегированного пользователя `app`, а не от `root`. Это отличная практика!

## 2. Инфраструктура и Docker (Уровень: Высокий 🟢)
- **Управление секретами:** `docker-compose.prod.yml` не содержит паролей в открытом виде. Вместо этого используются Docker Secrets (`/run/secrets/...`). Утилита `scripts/generate-secrets.sh` отлично справляется с генерацией стойких 256-битных криптографических ключей.
- **Изоляция контейнеров:** Контейнеры Postgres и Redis настроены с флагами `no-new-privileges:true`, `read_only: true` и используют `tmpfs` для временных файлов. Это делает практически невозможным взлом хоста даже при компрометации СУБД.
- **Сеть:** База данных и Redis не пробрасывают порты наружу (`expose` вместо `ports`), они доступны только внутри внутренней Docker-сети для бэкенда.
- **Sentry / Glitchtip:** Интеграция с Sentry включена по умолчанию. Любые паники на бэкенде будут перехватываться и отправляться в вашу панель Glitchtip.

## 3. WebRTC и WebSockets (Уровень: Отличный 🟢)
- **Redis Pub/Sub:** Использование Redis Pub/Sub позволяет запускать несколько экземпляров бэкенда.
- **TURN REST API:** Уязвимость перехвата статического пароля Coturn устранена. Бэкенд на лету генерирует временные `username` и зашифрованные HMAC-SHA1 пароли для WebRTC подключений.

## 4. Reverse Proxy и SSL (Уровень: Хороший 🟢)
- **Защита Nginx:** В `nginx.conf` прописаны строгие лимиты (`limit_req_zone`, `limit_conn_zone`), что защитит от примитивных DDoS-атак уровня L7.
- **Заголовки безопасности:** Nginx отдает строгие заголовки `Strict-Transport-Security`, `X-Frame-Options: SAMEORIGIN`, `X-XSS-Protection`, блокирующие большинство Client-Side атак.
- **Let's Encrypt:** Написанный нами скрипт получения SSL автоматизирует выдачу доверенных сертификатов.

## ⚠️ Рекомендации (Что нужно помнить при деплое)
1. **Firewall (UFW):** При переносе на VPS убедитесь, что вы закрыли все порты снаружи, кроме `80` (HTTP), `443` (HTTPS), `3478`, `5349` (TURN) и `7880-7882` (LiveKit). SSH-порт (22) рекомендуется изменить или закрыть за VPN/IP-whitelist.
2. **CORS_ORIGINS:** Обязательно впишите ваш реальный домен в файл `.secrets/cors_origins` перед стартом сервера, иначе Web-клиент не сможет делать запросы к бэкенду.
3. **Резервные копии:** Скрипты `backup-postgres.sh` присутствуют. Настройте `cron` на сервере для их ежедневного запуска с отправкой архива в облако (S3/Telegram).
